# 설계 변화와 구현 출처

## 기존 구현

기존 `ai-engine`과 `simulation`은 SLA 규칙 기반 원인 분석과 MAML/PPO 정책을 결합한 4라우터 데모다. 기존 절제 실험은 복구 성능이 주로 규칙 기반 분석에서 나온다는 것을 보여준다. 기존 모델과 역사적 결과는 이번 연구에서 수정하거나 다시 학습시키지 않는다.

## 사용자가 제공한 후속 연구

사용자는 `recovery_research` 파일 목록과 `SourceCutMixin`, `CalibratedForecast`, `CalibratedBaseline`, `cycle1` 등의 코드 일부를 제공했다. 완성된 `runner`, `cycle2`, `cycle3`, 지원 패키지와 결과 파일은 로컬·연결된 원격 브랜치에서 확보되지 않았다.

따라서 이번 지원 시뮬레이터와 누락된 로직은 **제공된 스니펫과 연구 의도를 바탕으로 새로 구현**한다. 원본을 복원했거나 과거 실행을 재현했다는 뜻이 아니다. 실행 manifest의 `implementation_origin`에도 이를 남긴다.

## 실험 전에 고정한 후보

| 이름 | 역할 | 검증하려는 가설 |
|---|---|---|
| `fixed`, `verified`, `hold10` | 고정 대기 / 관측 검증 / 긴 관측 검증 | 복잡한 예측 없이 기다리는 것만으로 충분한지 비교 |
| `forecast` / `cycle1` | 보고된 수요로 정상 비용 복귀를 예측 | 수요 편향에 취약할 수 있음 |
| `calibrated_forecast` / `cycle2` | source-cut 보정 후 동일한 예측 | 유효한 보존 조건에서 편향 문제를 줄일 수 있음 |
| `causal_calibrated_forecast` / `cycle3` | 보정 + 명령 이후 생성된 관측으로 완료 확인 | 조기 완료와 관측 지연의 교환 관계를 바꿀 수 있음 |
| `calibrated_fixed`, `calibrated_verified`, `calibrated_hold10` | 단순 기준에도 같은 보정 제공 | 보정의 이득을 예측 제어기의 이득과 혼동하지 않기 |

cycle 번호는 사용자 파일명에 맞춘 후보 구분이다. 이번 테스트 결과를 본 뒤 차례로 후보를 개선했다는 의미가 아니다. 모든 후보를 평가 전에 정하고 함께 공개한다.

## 구현 경계

`recovery_control`은 명령 적용 지연, 이전/새 경로의 잔류 혼합, 관측 지연·누락·편향을 모델링한다. `recovery_lifecycle`과 `recovery_completion`은 관측과 현재 시각만으로 판단한다. 실제 수요, 명령 적용 시각, 잔류 경로 상태는 평가기만 읽는다.

시나리오 교란은 seed·tick·항목으로 결정한다. 정책별 관측 횟수나 난수 소비가 다른 정책의 미래 교란을 바꾸지 않도록 한다. 같은 시나리오라도 제어 행동이 달라지면 실제 부하와 관측값은 달라지는 것이 정상이다.

보정은 첫 유효 표본, 초기 비용, 신선도, 배경 트래픽 경로 조건을 검사한다. 조건을 어기면 추정의 유효성을 주장하지 않고 원래 입력으로 돌아가며 이유를 기록한다. 제어기 완료 선언과 평가기의 실제 복구·원상복귀 판정은 따로 기록한다.

## 결과 해석

고정 test bank를 여러 번 보며 임계치를 고르지 않는다. 정확성 버그가 발견되면 기존 결과를 몰래 교체하지 않고 수정 사실·source hash·다시 실행한 이유를 기록해야 한다. 특정 방법이 항상 이기는 결과를 수용기준으로 두지 않는다. 무효 조건, 시간 초과, 과도한 대기, 부수 피해도 연구 결과다.
