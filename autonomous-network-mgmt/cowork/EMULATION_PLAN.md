# 에뮬레이션·토폴로지 확장 계획 (EMULATION_PLAN)

> 작성일: 2026-10-07
> 선행 문서: `ROADMAP.md` §8(이 환경에는 학습이 기여할 자리가 없다), `AUDIT_2026-09-09.md`
> 대상: ROADMAP §8의 선택지 **B(문제를 어렵게)** 를 어떻게 할 것인가. 두 갈래가 있고
> 성격이 전혀 다르다 — 토폴로지를 키우는 것과, **실제 라우팅 스택을 돌리는 것**.
>
> **이 문서는 계획이다. 아직 아무것도 구현하지 않았다.**

---

## 0. 출발점

### 0.1 왜 이 문서가 필요한가

`ROADMAP.md` §8이 측정으로 확정한 것: **이 환경에는 학습이 기여할 자리가 없다.** 관측만 쓰는
한 줄 규칙("지연 상위 2개 노드를 잇는 링크에 cost 100")이 미학습 링크까지 6개 전부 100%
복구한다. 커리큘럼·보상·baseline을 어떻게 고쳐도 바뀌지 않는다.

그 다음은 둘 중 하나다 — 학습을 포기하거나, **문제를 바꾸거나.** 이 문서는 후자의 설계다.

### 0.2 그런데 먼저, 메울 구멍이 하나 있다

`simulation/topology.py`(미사용 Mininet 참조 구현)를 읽으면 이렇게 되어 있다:

```python
# 라우터 역할 스위치 (실장비 없이 OVS로 대체)
r1 = net.addSwitch("r1", dpid="0000000000000001")
```

**OVS 스위치다. L2다. OSPF가 없다.** 운영 시뮬레이터(`metric_generator.py`)도 마찬가지로
cost 숫자를 바꾸면 스트레스 스칼라가 변하는 모형이며, LSA도 SPF 계산도 인접성(adjacency)도
없다.

이 프로젝트는 **"OSPF LSA 위조 탐지"를 핵심 주장으로 내세운다.** 그런데 OSPF가 어디서도 실제로
돌지 않는다. `ospf_security.py`는 위조 LSA의 *형태*를 규칙으로 판정할 뿐, 진짜 LSA를 받아본
적이 없다.

> 문제를 어렵게 만들기 **이전에**, 이미 주장하고 있는 것을 실제로 하는 쪽이 먼저다.

### 0.3 측정된 사실 (이 계획의 근거)

| 측정 | 값 | 출처 |
| --- | --- | --- |
| 한 줄 규칙의 복구 성공률 (K4, 6링크) | **100%** | `v2_design_check.py` V-2a |
| 최고 상수 행동 | 25% | 같음 — 상태는 봐야 하지만 **적응할 것이 없다** |
| 8노드·동시 장애 1건에서 휴리스틱 적중 | **1.000** | `topology_scaling_probe.py` — **노드만 늘려선 안 된다** |
| 8노드·동시 2건 (무작위 현) | 0.675 | 같음 — **동시 다중 장애**가 깨뜨린다 |
| 실제 네트워크에서 동작 | **없음** | `ROADMAP.md` §0 |

## 1. 원칙

1. **통과 조건을 먼저 적고 시작한다.** 각 단계에 "여기서 멈춘다"는 조건이 있다. 없으면
   어떤 결과가 나와도 다음 단계로 가게 되고, 그건 측정이 아니라 소망이다.
2. **어렵게 만든 뒤에 보고하지 않는다.** §8의 음성 결과(현 환경에 학습이 불필요)는 **이미
   보고를 마쳤다**. 그 뒤에 환경을 바꾼다. 순서를 뒤집으면 "학습이 이기도록 환경을 고쳤다"가
   된다.
3. **축소 모형의 수치를 운영 수치로 쓰지 않는다.** `topology_scaling_probe.py`는 ECMP 라우팅도
   트래픽 수요도 없다. 모든 숫자는 운영 시뮬레이터에서 **다시 재야** 한다.
4. **리팩터링과 동작 변경을 같은 커밋에 섞지 않는다.** 섞으면 결과가 달라졌을 때 원인을
   가릴 수 없다.
5. **기존 결과를 지우지 않는다.** K4 결과는 §8 음성 결과의 근거다. `_k4` 접미사로 보존하고
   병기한다.

## 2. Track E8 — 8노드 토폴로지

### 2.1 목적

진단 모호함을 만들어 학습이 기여할 수 있는 자리를 만든다. **빠른 학습 속도를 유지**하는 것이
이 트랙의 존재 이유다 (Track FRR은 그걸 못 한다 — §3.3).

### 2.2 그래프 선택 — 측정된 후보

`topology_scaling_probe.py`로 잰 값 (**축소 모형**, ECMP 없음):

| 그래프 | 차수 | 동시 2건 적중 | 해결% | 동시 3건 적중 | 해결% |
| --- | --- | --- | --- | --- | --- |
| 탐침의 무작위 현 | 3.0 | 0.675 | 57.5 | 0.695 | 20.0 |
| C8(1,4) 대칭 | 3.0 | 0.811 | 87.5 | 0.777 | 37.5 |
| C8(1,3) 대칭 | 4.0 | 0.802 | 97.5 | 0.659 | 67.5 |
| 고정 A (현 r1-r4, r2-r6, r3-r7, r5-r8) | 3.0 | 0.840 | 90.0 | 0.737 | 25.0 |
| 고정 B (현 r1-r3, r2-r5, r4-r7, r6-r8) | 3.0 | 0.898 | 87.5 | 0.825 | 17.5 |
| **고정 C (현 r1-r5, r2-r4, r3-r6, r1-r7)** | **2~4** | **0.691** | **70.0** | 0.657 | 15.0 |

**대칭 그래프는 뚜렷하게 쉽다.** 모든 노드의 차수가 같으면 스트레스 평균이 균일해 지연 상위
2개가 깨끗하게 나온다. 탐침의 무작위 현 수치(0.675)를 보고 C8(1,4)를 골랐다면 실제로는
0.811짜리를 집었을 것이다 — 구체적 그래프를 따로 재야 하는 이유다.

**제안: 고정 C.** 차수가 2~4로 불균일해 가장 어렵고(0.691), 해결률 70%로 여지가 남는다.
실제 네트워크도 차수가 균일하지 않다.

```
링(r1-r2-…-r8-r1) 8개 + 현 4개: r1-r5, r2-r4, r3-r6, r1-r7
→ 노드 8, 링크 12, 관측 2×8+12 = 28, 행동 12×5 = 60
```

### 2.3 미해결 쟁점 — TRAIN/TEST 분할

| 선택 | 장점 | 대가 |
| --- | --- | --- |
| **대칭 그래프** | 모든 링크가 구조적으로 동등 → 미학습 링크 성능이 공정 | 문제가 쉬워진다 (0.81) |
| **비대칭 (고정 C)** | 어렵다 (0.69), 현실적 | 링크마다 고유 난이도가 달라 **"미학습 링크 성능"이 링크 난이도와 섞인다** |

**결정 필요.** 비대칭으로 간다면 차수·위치를 맞춘 **층화 분할**(TRAIN 8 / TEST 4, 각 집합에
차수 2·3·4 링크를 고르게)이 최소 조건이고, 일반화 수치를 읽을 때 그 한계를 병기해야 한다.

### 2.4 영향 범위 (코드에서 확인함)

**자동으로 따라오는 것** — 차원이 이미 상수에서 유도된다:

```python
OBS_DIM    = 2 * N_NODES + N_LINKS      # 14 → 28
ACTION_DIM = N_LINKS * len(OSPF_COSTS)  # 30 → 60
```

**손으로 고쳐야 하는 것**:

| 위치 | 내용 |
| --- | --- |
| `ai-engine/topology.py` | `NODES`, `LINKS` |
| `simulation/metric_generator.py` | `NODES`, `LINKS_LIST` (별도 배포 단위라 중복 — 자가 테스트가 일치 확인) |
| `orchestrator-service/.../AiEngineClient.java` | `NODE_ORDER`, `LINK_ORDER`, 14차원 주석 |
| `dashboard.html` / `index.html` | JS의 `NODES`/`LINKS`, 노드 카드 4개, OSPF 그리드 6칸 |
| **TRAIN/TEST 분할 — 7개 파일에 중복** | `run_experiment`, `stress_test`, `persistent_buffer_test`, `collapse_diagnosis`, `training_design_audit`, `critic_check`, `v2_design_check` |

마지막 줄이 가장 위험하다. 7군데 복붙이라 한 군데만 놓쳐도 조용히 틀린다 — 2026-09-13에
`train_links=None` 하나로 평가 누수가 났던 자리와 같은 종류다.

### 2.5 단계와 통과 조건

| 단계 | 내용 | **통과 조건 (못 넘으면 멈춘다)** |
| --- | --- | --- |
| **E8-0** | TRAIN/TEST 분할을 `topology.py` 단일 출처로. 동작 변경 없음 | 기존 결과가 **그대로 재현** |
| **E8-1** | 토폴로지 파라미터화. 기본값은 여전히 K4 | K4 결과가 **비트 단위로 동일** (20-iter 스모크 해시 일치) |
| **E8-2** | 8노드 전환. `OBS_VERSION` 1→2, `ACTION_VERSION` 1→2, `SIM_VERSION` 3→4. Java·대시보드 동기화 | — |
| **E8-3** | **운영 시뮬레이터에서 휴리스틱 재측정** | **휴리스틱 적중률이 유의하게 떨어질 것.** 여전히 ~100%면 **여기서 멈추고 보고한다** |
| **E8-4** | 에피소드 길이 재측정 (K4에서 잰 8은 무효) | — |
| **E8-5** | 요인 실험 | E8-3을 통과했을 때만 |

**E8-3이 이 트랙의 생사다.** 축소 모형에 ECMP가 없으므로, 운영 시뮬레이터에서는 결과가 다를
수 있다.

### 2.6 비용

E8-0·E8-1이 전체의 절반쯤이고 대부분 리팩터링이다. 건너뛰고 싶어지지만 건너뛰면 7군데 중
하나를 놓친다. 학습 속도는 유지된다(스텝당 ~1ms).

## 3. Track FRR — 실제 라우팅 스택

### 3.1 목적

§0.2의 구멍을 메운다. **라우터를 직접 구현하지 않는다** — 실제 운영에 쓰이는 라우팅 데몬을
컨테이너로 띄운다.

| 층 | 무엇 | 작업 성격 |
| --- | --- | --- |
| 0 (현재) | 스트레스 스칼라, 패킷 없음, 라우팅 프로토콜 없음 | — |
| **1 (이 트랙)** | **FRRouting / BIRD / VyOS 컨테이너** — 진짜 OSPF | containerlab YAML + 노드별 FRR 설정 |
| 2 | 실제 데이터플레인 — iperf 트래픽 + `tc/netem` 장애 | 트래픽 생성기·계측 추가 |
| 3 | 벤더 이미지 — Arista cEOS, Cisco CML, Juniper vMX | 라이선스·이미지 확보가 주 장벽 |

FRR은 장난감이 아니라 실제 운영 스택이다(NVIDIA Cumulus Linux 등이 쓴다). 8노드 OSPF 랩이면
토폴로지 YAML 한 장과 FRR 설정 8개 수준이다.

### 3.2 얻는 것

- **진짜 OSPF**: LSA, SPF 계산, 인접성, 실제 수렴 타이밍, 실제 라우팅 테이블
- **LSA 위조를 흉내가 아니라 실제로 주입**할 수 있다 → `ospf_security.py`의 주장이 처음으로
  근거를 갖는다
- **진단 모호함이 자연히 생긴다** — 수렴 지연, 경로 플래핑, 연쇄 장애. 인위적으로 만든 것이
  아니므로 §8이 경계한 비판에서 자유롭다
- `ROADMAP.md` §0의 "실제 네트워크에서 동작: **없음**"을 처음으로 공략한다

### 3.3 잃는 것 — 그리고 이것이 핵심 제약

한 스텝이 "cost 변경 → LSA 플러딩 → SPF 재계산 → FIB 설치"를 기다려야 한다.

| 스텝당 수렴 (가정) | PPO 50,000 스텝 1회 | 요인 실험 6변종 |
| --- | --- | --- |
| 1ms (현재) | 1~2분 | ~50분 |
| 100ms (타이머 극한 튜닝) | ~1.4시간 | ~8시간 |
| 500ms (현실적) | **~7시간** | **~42시간** |
| 2s (기본 타이머) | ~28시간 | 1주일 |

> **위 표는 측정이 아니라 산술 추정이다.** 실제 수렴 시간은 FRR 랩을 세운 뒤 재야 하고,
> 그 측정 자체가 FRR-2의 첫 과제다.

**RL 학습을 이 위에서 직접 돌리는 것은 현실적이지 않다.** 이 프로젝트만의 문제가 아니라
네트워크 RL 연구 전반의 제약이다.

### 3.4 단계와 통과 조건

| 단계 | 내용 | **통과 조건** |
| --- | --- | --- |
| **FRR-0** | containerlab 토폴로지 + FRR 설정 작성. 기동 없이 문법 검증까지 | 설정이 문법상 유효 |
| **FRR-1** | 랩 기동, OSPF 수렴 확인 | 전 노드 Full 인접성, 라우팅 테이블 일치 |
| **FRR-2** | **수렴 시간 측정** (cost 변경 → FIB 반영까지) | §3.3 표를 실측으로 대체 |
| **FRR-3** | SNMP/gNMI 수집 어댑터 — `mock_snmp_agent`와 같은 인터페이스 | 기존 폐쇄 루프가 **코드 변경 없이** 붙는다 |
| **FRR-4** | **규칙 기반 RCA를 실제 OSPF에 걸어 측정** | 시뮬레이터 결론이 옮겨가는가 — **이 트랙의 핵심 질문** |
| **FRR-5** | LSA 위조 실주입 → `ospf_security.py` 검증 | 탐지 규칙이 실제 LSA에서 동작 |

**FRR-4가 이 트랙의 핵심이다.** 지금 TTR 6.88은 이 시뮬레이터 안에서만 의미가 있다. 실제
라우팅 스택에서 같은 측정을 하면 **"시뮬레이터 결론이 옮겨가는가"**를 처음으로 답한다.

## 4. 두 트랙의 관계 — 2단 구조 (sim-to-real)

```
  빠른 추상 시뮬레이터 (Track E8)        FRR/containerlab 랩 (Track FRR)
  ├─ 역할: 학습                          ├─ 역할: 검증
  ├─ 스텝당 ~1ms                         ├─ 스텝당 100ms~2s (실측 필요)
  └─ 수만 스텝 가능                       └─ 수백 에피소드면 충분
```

검증 단계는 학습이 아니라 평가이므로 느려도 된다. 이 구조가 표준적인 sim-to-real 배치이고,
**두 트랙이 서로를 대체하지 않는다** — E8은 학습이 가능한 난이도를, FRR은 결론의 이전
가능성을 담당한다.

## 5. 우선순위

| 순위 | 트랙 | 근거 |
| --- | --- | --- |
| **1** | **FRR-0 ~ FRR-2** | §0.2의 신뢰성 구멍이 먼저다. 주장하는 것(OSPF)을 실제로 하지 않는 상태에서 난이도를 올리는 건 순서가 틀렸다 |
| 2 | E8-0, E8-1 | 리팩터링. 어느 트랙으로 가든 필요하고, 동작 변경이 없어 안전하다 |
| 3 | FRR-3, FRR-4 | 시뮬레이터 결론의 이전 가능성 — ROADMAP §0의 최대 미검증 항목 |
| 4 | E8-2 ~ E8-5 | 학습의 자리를 만드는 작업. FRR-4가 "시뮬레이터 결론이 안 옮겨간다"고 하면 **설계 전제가 바뀌므로** 그 뒤에 해야 한다 |
| 5 | FRR-5 | LSA 위조 실검증 |

**E8보다 FRR이 앞선다**는 것이 이 계획의 판단이다. E8은 "학습이 필요해지도록 환경을 어렵게"
만드는 것이고, FRR은 "원래 주장하던 것을 실제로" 하는 것이다. 후자가 먼저다.

| **E8-3에서 휴리스틱이 안 깨진다** | 멈추고 보고. 토폴로지를 더 키우거나 다른 축(링크 용량 제약, 부분 관측)으로 전환 |
| **FRR 수렴이 너무 느려 검증조차 버겁다** | OSPF 타이머 튜닝(`ispf`, `spf-delay`) 후 재측정. 그래도 느리면 평가 에피소드 수를 줄이고 그 사실을 병기 |
| **FRR-4에서 시뮬레이터 결론이 안 옮겨간다** | **그것이 결과다.** TTR 6.88의 유효 범위를 "이 시뮬레이터 안"으로 명시하고 그대로 보고 |
| 7군데 TRAIN/TEST 중복에서 누수 재발 | E8-0을 **먼저** 한다. 건너뛰지 않는다 |
| 기존 결과·체크포인트 무효화 | `_k4` 접미사로 보존. 체크포인트는 차원이 달라 **로드 자체가 안 된다**는 점을 문서화 |
| "어렵게 만들어 학습이 이기게 했다"는 비판 | §8 음성 결과를 **먼저 보고 완료**했다. FRR을 E8보다 앞에 둔 것도 같은 이유 |

## 7. 하지 않을 것

- **라우터·스위치를 직접 구현하지 않는다.** FRR/BIRD/VyOS를 쓴다. OSPF 구현은 연구 주제가
  아니다
- **벤더 이미지(Tier 3)로 가지 않는다.** 라이선스 장벽 대비 얻는 것이 적다
- **FRR 위에서 RL을 학습시키지 않는다.** §3.3의 산술이 말리고 있다. 검증 전용이다
- **E8과 FRR을 한 번에 섞지 않는다.** 둘 다 바꾸면 결과 차이의 원인을 가릴 수 없다
