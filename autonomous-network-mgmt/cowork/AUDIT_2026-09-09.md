## 1. 발견된 문제

`PROJECT_OVERVIEW.md` §7에 이미 기록된 한계(시뮬레이션 한계, CICDDoS 피처 문제, 미검증 영역 등)는

### 1.1 실험 결과의 신뢰성에 직접 영향하는 문제

#### P1. 시뮬레이션 시간이 "관측 호출 횟수"로 흐른다 → TTR이 측정 스크립트에 의존

- **근거**: `simulation/metric_generator.py:124,129` — `get_node_metrics()`/`get_all_metrics()`가
  호출될 때마다 `_update_link_stress()`로 스트레스를 1스텝 진행시킨다. 벽시계 시간과 무관하며
  실험 스크립트의 `time.sleep(0.6)`은 물리적으로 아무 효과가 없다.
- `experiments/stress_test.py:99`, `ablation_study.py:40`, `persistent_buffer_test.py:81`이
  `/auto-step`(내부에서 `/metrics` 1회) 뒤에 **검증용 `/metrics`를 한 번 더** 호출한다 →
  OODA 1사이클당 시뮬레이터 2틱 진행.
- **재현** (`scratch/rca_trace.py`, HTTP 없이 `metric_generator` + `diagnose()` 직접 구동,
  analytics-only, 50 ep):

  | 사이클당 틱 | 평균 TTR |
  | --- | --- |
  | 2 (현재 측정 방식) | **3.94** — 보고치 `ablation_study.json` analytics_only 3.88과 일치 |
  | 1 (`/auto-step`만) | **6.68** |

- **의미**: 보고된 TTR 3.78~3.88의 절반 가까이는 측정 스크립트 자신이 회복을 가속한 결과다.
  대시보드나 collector(5초 폴링) 같은 관측자가 하나 더 붙으면 수치가 또 달라진다.
  `/metrics/<node>` 단일 노드 조회도 전체 링크를 진행시킨다.

#### P2. "RCA 정확도 100%"는 첫 사이클만 측정 — 2번째 사이클부터 정상 링크를 망가뜨림

- **근거**: `stress_test.py:130` `root_match = (first_root == link)`. 첫 판정만 본다.
- 2번째 사이클부터 정답 링크는 cost 100이 되어 `unhandled_links`에서 빠지고
  (`anomaly_detector.py:61`), `api_server._root_cause_analysis()`(`:240-265`)는 남은 인접 링크 중
  `(-shared, cost)` 최소 = **알파벳순 첫 링크**를 근본 원인으로 지목한다.
- **재현** (같은 스크립트): analytics-only 50 ep에서 **정상 링크 cost를 100으로 올린 횟수 112회**
  (에피소드당 ~2.2회). 예: `link=r1-r3 → actions=['r1-r3@100', 'r1-r2@100', 'r1-r4@100', 'r2-r3@100']`
- **의미**: TTR만 재고 "불필요한 라우팅 변경 횟수"라는 비용은 어디에도 기록되지 않는다.
  실망에서는 매 사이클 OSPF 재수렴을 유발하는 행동이다. combined 모드에서는 override 조건
  (`nodes_sharing_root >= 2`)이 2사이클째부터 안 맞아 MAML 행동이 그대로 나가는데,
  `persistent_buffer.json`이 기록한 2차 행동 `r1-r2@200`도 같은 종류의 부수 피해다.

#### P3. 폐쇄 루프 Orient에 IsolationForest가 실제로 쓰이지 않음 (문서-코드 불일치)

- **근거**: `api_server.py:343` — `/auto-step`은 `detector.update()`만 호출하고
  `detector.is_anomaly()`는 호출하지 않는다. 판정은 `diagnose()`의 SLA 규칙
  (지연 > 50 ms, 손실 > 1 %)뿐이다. IsolationForest는 Java 경로 `/anomaly`(`:279`)에서만 쓰인다.
- 그런데 README 43·53·251행, `experiments/experiment_report.md` §2.1·§2.2,
  `stress_test.py:156`("IsolationForest + adjacency scoring")이 폐쇄 루프가 IF 기반이라고 서술한다.
  README "핵심 기여 3 — 비지도 IsolationForest를 조합해 알려지지 않은 이상 패턴까지 커버"는
  폐쇄 루프에 관한 한 사실이 아니다.

#### P4. SecurityAnomalyDetector — 평가 누수 + 학습셋 오염

- `experiments/validate_security_detector.py:82-83`, `api_server.py:569-577` —
  `update()` **후** `detect()` 순서라 판정 대상 샘플이 이미 학습셋(최근 200개)에 포함된 채 판정한다.
- `anomaly_detector.py:129` — 레이블과 무관하게 모든 샘플로 재학습한다. 공격이 지속되면
  IsolationForest가 공격을 '정상'으로 학습한다.
- `contamination=0.05` vs CICDDoS2019 공격 비율 0.56 — 모델 가정이 데이터와 맞지 않는다.
- **의미**: README는 F1 < 베이스라인의 원인을 피처 추출에만 두고 있으나 이 구조적 문제도 함께
  작용한다. (contamination 조정은 "지표 튜닝"이므로 하지 않고 문서화만 한다.)

#### P5. MAML 학습에 탐색(exploration)이 없음

- **근거**: `agents/few_shot_agent.py:75` — 학습용 `_collect_episode()`가 항상 `argmax`로
  행동을 고른다. REINFORCE는 정책에서 **샘플링**해야 gradient 추정이 유효하다. 결정론적 선택이면
  같은 상태에서 늘 같은 행동만 보므로 advantage가 행동의 좋고 나쁨이 아니라 상태 차이를 반영한다.
- **의미**: `maml_only` 성공률 24%의 유력한 원인. 현재의 "MAML 기여가 확인되지 않음" 결론이
  MAML 자체의 한계인지 구현 결함인지 구분할 수 없다.

#### P6. Support buffer 라벨 오염

- **근거**: `api_server.py:372` — 이상이 없는 스텝에서는 `_prev_action`이 갱신되지 않아 다음 스텝에
  `(obs, 실행하지 않은 stale action, reward)`가 버퍼에 들어간다. 첫 이상 직전 샘플은
  항상 `action=0`(`r1-r2@10`)으로 기록된다(`:101` 초기값).
- **의미**: MAML inner-loop가 잘못된 (행동 → 보상) 쌍으로 적응한다.

#### P7. NO-OP 행동이 없음

- 행동 30개가 전부 cost 변경이다. 오프라인 평가(`run_experiment.py`)와 PPO 학습에서 에이전트는
  정상 상태에서도 매 스텝 어떤 링크의 cost를 반드시 바꿔야 한다.
- Java 경로 `OrchestrationService.onMetric()`도 `isAnomaly` 결과를 로그만 남기고
  이상 여부와 무관하게 5초마다 행동을 실행한다.
- **제약**: `FIX_PLAN.md` §0.2-5가 "NetworkEnv 30 행동"을 공개 시그니처로 못 박았으므로
  행동 공간은 바꾸지 않는다. Java 경로의 "이상 없으면 무행동"만 고치고 나머지는 한계로 기록한다.

### 2.2 태스크 상세

#### A1. 시뮬레이터 시간을 관측에서 분리

- `metric_generator.tick()` 신설. `get_all_metrics()`/`get_node_metrics()`/`get_security_metrics()`는
  **순수 조회**(스트레스 갱신 없음). `random.Random` 인스턴스를 두고 `reset_state(seed=)`로 재현 가능.
- `mock_snmp_agent`: `POST /debug/tick` 추가, `POST /debug/reset` body `{"seed": N}` 지원.
  `SIM_CLOCK` 환경변수 — `lockstep`(기본, tick 요청으로만 진행) / `realtime:<ms>`(백그라운드 스레드가
  주기적으로 tick — Java·대시보드 데모용).
- `api_server /auto-step`: 사이클 시작 시 `POST /debug/tick` 1회 → 관측. 사이클당 정확히 1틱.
  기존 시맨틱(관측이 곧 1틱)과 동일하되, 외부 관측이 시간을 진행시키지 않는다.
- `NetworkEnv.step()`: cost 적용 → `tick` → 관측. `reset()`은 tick 없이 관측.
- 실험 스크립트: 검증용 `/metrics`는 이제 순수 조회. `time.sleep`은 무의미하므로 제거.
- 검증: `metric_generator.py` `__main__` 자가 테스트(조회 100회 후 스트레스 불변, tick 후 변화, seed 재현).
- 완료 기준: 위 자가 테스트 통과, `/auto-step` 응답 스키마 불변, 재현 스크립트에서 1틱/사이클 확인.

#### A2. RCA 2사이클 이후 오판 수정 + 부수 피해 지표

- `_root_cause_analysis()`를 `anomaly_detector.root_cause_analysis()`로 이동(api_server는 import).
  규칙:
  1. 위반 노드 **전부**에 인접한 `unhandled` 링크가 있으면 → 그것(가장 낮은 cost). 확정 근본 원인.
  2. 없고, 위반 노드 전부에 인접한 **이미 대응된**(cost ≥ 100) 링크가 있으면 → `None`
     ("이미 조치됨, 회복 대기"). 정상 링크를 건드리지 않는다.
  3. 둘 다 없으면 기존 폴백 `(-shared, cost)` 최소.
- `/auto-step` analytics-only(`disable_maml`) 경로: `root_cause`가 `None`이면 **무행동**
  (`act.applied=False, reason="recovering"`). 기존의 `unhandled[0]` 폴백 삭제.
- 실험 3종에 지표 추가: `wasted_actions`(주입 링크가 아닌 링크의 cost 변경 횟수),
  `rca_all_cycles_ok`(모든 사이클에서 root cause ∈ {주입 링크, None}). 기존 `root_match`는 유지.
- 검증: `anomaly_detector.py` `__main__`에 3규칙 케이스 + 2사이클 시나리오 자가 테스트.
- 완료 기준: 재현 스크립트에서 analytics-only `wasted_actions`가 0, 자가 테스트 통과.
  TTR 변화(전/후)를 §3에 기록 — **나빠져도 그대로 기록**.

#### A3. MAML 학습 탐색 + support buffer 라벨

- `_collect_episode(..., sample=True)`: 학습 시 `Categorical(logits).sample()`, 추론(`act`)은 argmax 유지.
- `api_server`: `_prev_action: int | None`. 행동을 실행하지 않은 스텝은 `None` → 다음 스텝에서 버퍼에
  넣지 않는다. `/reset-buffer`도 `None`으로.
- torch 설치 가능 시 MAML 재학습(500 iter, 기존 하이퍼파라미터 그대로 — **튜닝 금지**) 후
  오프라인 평가·ablation `maml_only`를 재측정. 불가 시 "체크포인트는 수정 전 학습분"을 명시.
- 완료 기준: 학습 코드가 샘플링 사용, 버퍼에 stale action 없음(자가 테스트), 전/후 수치 §3 기록.

#### A4. 조용한 실패 제거 + 루프 락

- `_fetch_snmp()` 실패 → `HTTPException(503, "SNMP agent unreachable")`. `/diagnose` 동일.
- `_apply_ospf()` → `bool` 반환, `act.applied`에 반영, 실패 시 `act.error` 포함.
- `NetworkEnv` HTTP 모드: 관측 실패 시 예외(가짜 정상값 삭제).
- Java `AiEngineClient.isAnomaly()`: 예외를 `RuntimeException`으로 전파, `OrchestrationService`가
  `log.error` 후 해당 라운드의 이상 판정을 "unknown"으로 처리. `anomaly-check-enabled=true`일 때
  **이상 노드가 하나도 없으면 orchestration 스킵**(폐쇄 루프 B와 동일 정책).
- `api_server`: `threading.Lock`으로 `/auto-step`·`/reset-buffer`·`/action` 상태 접근 직렬화.
  `metric_generator`: 모듈 락으로 tick/set/inject 직렬화.
- 검증: `mvn -q compile` 양쪽, FastAPI TestClient로 SNMP 다운 시 503 확인.

#### A5. SecurityAnomalyDetector 평가 순서

- `/security/detect`, `validate_security_detector.py`: **`detect()` → `update()`** 순서로 변경.
  `update()/detect()` 시그니처(6인자) 불변.
- `contamination` vs base-rate 불일치와 "공격 지속 시 공격을 정상으로 학습" 문제를 README 한계에 추가.

  "update→detect 순서로 측정된 값, 다음 재실행은 detect→update" 명시.
